# 语音下一首执行反馈专项验收（2026-11-15）

## 结论及原始证据
旧 music.next 处理器调用 next()，返回 None；通知将其解释为未知。隔离加载施工前控制器的真实注册方法，首次探针 1 failed，原样复现“已请求播放下一首／尚未收到完成确认，请查看对应页面”。这证明反馈契约缺失，不证明播放失败。

## 实施边界
- 保留 next() 的旧返回值、300ms 防抖、队列选曲、E→D、自然接续、随机/单曲循环以及自动跳过行为。
- MUSIC_NEXT 仅 voice 来源使用 NextFeedback；自然语义的 guarded next 使用同一适配器。明确语音下一首通过现有 execute_async，避免在 GUI/识别调用线程等待 IPC。
- 控制器只补充选择、空队列、防抖、锁忙、解析和 loadfile 证据；既有诊断阶段也送给观察器。观察器不选歌、不重试网络、不执行第二次切歌。
- 每个控制器至多一个按需观察线程、一个当前请求，最长30秒；正常起播后退出，模块停止有界回收。真实 MPV 属性读取复用原管道/RPC，以40ms锁预算和40ms响应预算读只读属性。
- 同一 notification ID + owner + play_request_id 绑定；通用 None 和外层自然语义返回不能覆盖已发布阶段。旧操作更新其原记录，不更新新语音；清空后不复活。
- 非 voice 的原 UI/自然接续仍直接调用原 next()，返回 None。CommandBus 路由没有重写，语义提取、学习体系、LoL、网络设置、播放器解码未改。

## 能够确认的状态
1. 已选中：记录真实播放代次后显示正在解析并加载。
2. loadfile error=success：只显示“播放器已接受下一首，正在确认起播”，不能算成功。
3. 真正起播：新 MPV playlist entry ID（包含重复路径）、该条目的文件与当前歌曲一致、idle=false、pause=false，连续观测 time-pos 前进，且完成前再次复核请求代次及语音操作。
4. 队列为空/顺序末尾：明确没有下一首；不虚构。
5. 300ms重复请求：明确忽略；锁忙/播放器不可用分别提示。
6. URL无结果/异常、MPV拒绝：失败；IPC无确认：未知。预算到期分别显示解析/加载超时或已接受但起播仍未确认。旧请求/新语音覆盖：停止确认，不宣称成功。
上述“起播”是MPV实际进度证据，不是扬声器物理出声证明。观察超时不等于取消底层网络请求；底层仍由原代次守卫隔离，不擅自修改播放算法。
