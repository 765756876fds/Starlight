## 音乐停止：现场证据与边界

分析对象为项目 `logs` 下最新当天JSON、print、app/error日志，并检索整个 `ongoing_debug.log`。后者没有 `[Music]`、`[mpv]`、`end-file`、`auto_next`、`loadfile`、`queue_pos` 标记，是LoL面板调试日志，不能用于猜音乐队列状态。

取一段明确的停止相关窗口（歌曲名、路径均不披露）：

| 时间 | 现场记录 |
| --- | --- |
| 17:39:04.099 | `mpv loadfile ok`，命令被接受 |
| 17:44:01.889 | 检测到播放结束，准备自动下一首 |
| 17:44:01.889—01.900 | 实时idle确认，调用next并返回 |
| 18:02:50.991 | 此后第一条新的 `mpv loadfile ok` |

当天18:08、18:10、18:11、18:18、18:23、18:26也有自动下一首调用。`next()完成`只代表函数返回，不等于已有下一曲开始播放。旧日志没有当时的队列大小、索引、播放模式，也没有原始end-file原因；该窗口未见在线解析失败、连续失败保护或播放器重启记录，但“未见记录”不能用来排除所有异常。

**结论：尚不能把用户实际停止定性为A—F中的哪一项。** 顺序队尾正常停止与某些未记录的状态均有可能，不能凭印象修改算法。

本批只补两处必要诊断，未改变音乐播放逻辑：

1. `MpvController._send_command` 遇到原本被跳过的end-file事件，记录白名单原因和整数entry ID；继续跳过事件，保留命令响应与既有idle轮询。日志写入失败不能吞掉IPC响应。不记录文件名/URL/原始消息。
2. `MusicController._auto_next` 调用前后记录模式、队列大小、索引及是否持有当前歌曲；`has_current_song`不冒充“正在播放”。不改变E→D、随机、单曲循环、跳过或防抖语义。

这些诊断不会补回历史证据，也不会让已运行的旧Python进程自动加载新代码。下一次在新版源码中复现时，才能结合新字段继续定性。
