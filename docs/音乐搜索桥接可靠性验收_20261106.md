## 原因与修复

1. bridge.js全源搜索原来串行遍历Map的全部别名，同一插件可被调用多次，而且search没有单插件期限。一个异步挂起就能让整体超过Python15秒时限，也会阻止正常音源返回。现在按插件对象去重，独立执行并复用既有8秒期限，返回部分结果与具体timeout/plugin类别；正常空数组仍是成功空结果。
2. Python读取JSON后直接.get：null/数组等合法JSON会让读取线程异常退出。现在验证帧结构及字符串请求ID；非法行忽略，分段JSON继续由真实流按行接收。
3. 请求写入与进程刷新没有共同串行边界。现在写入、关闭、刷新和自动恢复共用轻量RLock；响应等待不占写锁。每条读取线程绑定创建它的进程，过期ready/旧EOF不能更新当前元数据或重启当前进程。
4. 原关闭不立即唤醒pending，进程异常退出也依赖超时。现在及时唤醒并移除请求，回收进程及标准流；沿用原有两个读取线程并做有界收尾，没有增加常驻线程。关闭后不再reload复活。
5. 插件console.log原来混入stdout。桥接进程把console的普通输出转到stderr；RPC响应继续单独写stdout。jsonrpc也拒绝非对象请求。没有改插件函数签名或Node版本。
6. 自动重启虽检查三次上限，实际未递增计数。新增探针修复前6次调用全部重启，修复后窗口内最多3次，转换也在同一锁保护下。

这些机制能够复现15秒桥接超时，但历史用户日志没有标记究竟是哪一个插件挂起，因此不能把历史故障唯一归因到本补丁。没有调查VPN或系统网络。

## 边界

- Promise期限只隔离等待结果，不撤销插件已经发出的HTTP；切换关键词沿用UI代次隔离，不能承诺物理取消外部请求。关闭所有者/刷新可结束旧Node进程，不为一次页面切换杀共享音源进程。
- 同步死循环阻塞Node事件循环时，Promise计时也无法运行，仍依赖原有进程级超时watchdog；不更换插件架构实现线程强制中断。
- 此次正常多插件并行请求数量取决于已加载插件数，未建立第二套调度架构。没有真实外网批量搜索；真实音源服务器、返回结构与HTTP可达性仍须自然使用验证。
- 窗口退出接线已核对MusicController.stop→manager.close→source.close；自动化重点验证该资源所有者回收与Qt晚结果隔离，不冒充真实Windows退出实测。
