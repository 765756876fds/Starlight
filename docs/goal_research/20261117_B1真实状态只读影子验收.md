## 2. 数据契约与六种结果

`contracts.py`定义Goal、GoalConstraints、WorldStateSnapshot、CapabilityEvidence、CandidatePlan、DecisionResult。仅支持LISTEN_MUSIC；未知目标不执行。候选含动作、前提证据、目标条件、来源、时间/TTL/可靠性、内容/队列变化、成本、偏好层级和选择/排除原因；只保存不透明资源/内容身份，不携带标题、路径、URL或完整语音。

资源证据三态：available / unavailable / unverified。过期、未来时间或不可靠证据自动视为unverified，不能用Python真假值代替判断。方案建议与目标已满足分开：

| 结果 | 必要证据 | 是否宣称目标已满足 |
| --- | --- | --- |
| NO_OP | 新鲜一致的音乐状态，真实MPV进度推进，已观察音乐在播，符合明确约束 | 是，仅对该快照 |
| RESUME_MUSIC | 可靠暂停状态、同一当前歌曲/path及播放代次，状态未过期，跨媒体策略允许 | 否，只建议恢复 |
| PLAY_PREFERRED | 个人资源存在/归属及特定歌曲的新鲜可播放能力证明，满足约束 | 否 |
| PLAY_CHART | 特定榜单内容及新鲜可播放能力证明，满足约束 | 否 |
| UNAVAILABLE | 有效快照内没有满足已知约束的计划 | 否；不是宣称所有网络来源永久不可用 |
| NEEDS_CLARIFICATION | 状态未知、证据不足/过期、冲突或尚未授权的跨媒体策略 | 否；部分原因表示待核验，不强迫用户回答技术问题 |

GoalConstraints覆盖明确不换内容、明确换内容、指定标签及排除资源。明确约束先筛选；保留有效当前体验优先，明确偏好先于历史，再比较成本。等价个人资源没有可靠胜出证据时澄清。新内容方案必须有特定content_ref，不能用一个泛泛“榜单可用”代替歌曲证明。

### SQLite只读的严格边界

使用`mode=ro&immutable=1`及只读authorizer，不运行迁移或写PRAGMA；缺失库不创建，损坏库不重命名/恢复。发现任何WAL或journal就拒绝主库快照，不将忽略WAL的旧数据当作实时状态；读前后核对文件大小/mtime，查询有进度预算。该方法是保守的离线文件读取，**不是活跃数据库的事务快照替代品**。

如果以后要读取活跃用户库，应由数据库所有者提供有界一致只读快照。本轮不为此修改MusicDatabase。收藏是否为空、可播放项数量都不能从拒绝读取的结果推断。

## 4. Provider与决策层

- CurrentSessionProvider：提出保持或恢复方案，不运行pause/resume。
- PersonalCollectionProvider：提出已读取的个人成员候选；明确保存到固定喜欢歌单属于证据，普通跳歌不等于不喜欢。只会将与当前已确认解码对象完全对应的成员升级即时能力，其他项保留未知。
- ChartProvider：只读取现成榜单候选。已有id/标题不能获得播放能力，也不能因没有现成缓存就宣布整个在线音源不可用。
- 统一decide检查代次、快照时效和硬约束，再做目标满足及方案比较。电影活跃/未知时，除不改变任何内容的NO_OP外，返回待澄清；不自行暂停电影或创造跨媒体偏好。

与V1的差异是：同一个已知LISTEN_MUSIC目标可选择不动作、恢复、偏好内容、榜单或拒绝。V1的直接推荐命令仍沿其已验收流程重新推荐；B1结果不会覆盖V1通知，也不会影响返回结果。

## 5. 实际读取与真实媒体验证

### 本机数据库：真实只读，聚合记录

按当前源码配置定位项目内音乐库和music_preferences.db，未查询其他用户目录：

- 音乐库存在`music.db-wal`（当时长度0）与SHM。仅凭伴随文件不能断言正在写入；B1按保守契约拒绝主库快照，inventory=unverified。**0项observed不是“没有收藏”**。
- 偏好库只读得到1项明确偏好、107条manual/legacy行为；可绑定的明确歌手偏好0项，读取了上限64项历史歌手证据。其他明确偏好维度没有被伪造为已支持。
- legacy是弱历史种子，不是用户确认喜好；自动推荐行为不进入此历史证据。没有将这些记录写入新库。
- 验证读取耗时2.6755ms；读取前后主库、偏好库、WAL和SHM文件SHA256全部一致。输出只有数量/原因，不记录具体歌名、歌手、歌单、路径或播放URL。

### 真正的独立MPV

生成静音WAV，使用现有MPV、独立进程与唯一IPC、`--no-config --ao=null --vo=null`；不连接用户播放器。只读端只允许4种get_property，使用独立连接，不占正式控制器回复流。测试建立播放/暂停属于测试准备，不是影子计划执行。

最终真实读取：播放中→NO_OP，暂停→RESUME_MUSIC建议；都保持原pause属性、队列和进程状态。测试后仅回收自己启动的进程，关闭IPC，无影子线程残留。不代表扬声器、真实在线URL或麦克风验收。

首次native验证2 failed/1 passed，保留`mpv-first.log`。原因是fixture只等待idle=false，尚未等到有效time-pos；真实诊断证明早期time-pos可为null。修正fixture等待明确就绪，同时增加null状态不得报playing的回归。

测量还发现固定20ms可能落在同一进度更新帧内：原型保守返回未知，测量断言失败。保留首次测量证据；读端改为最多150ms、受总预算限制的进度推进观察，不放宽“观察到进度才确认”的条件。正式MPV代码没有改。

## 6. 响应性、代次和零执行副作用

没有安装正式钩子，也没有新配置项。`ShadowObserver`仅供显式测试：最多一个工作线程、没有任务队列，忙时拒绝新观察，默认600ms预算，超时/关闭/旧代次结果丢弃。Qt主线程直接capture会被拒绝；GUI不等待结果。异常只返回固定错误码，不序列化可能含隐私的异常消息。

Qt测试注入受控慢读取，50次重复请求没有创建第二个工作线程，定时器持续响应；窗口关闭语义会丢弃结果。Python不能杀死忽略预算的第三方函数，close若未退出明确返回False，不冒充成功。正因任意外部回调仍有这一限制，本轮**选择不接正式语音钩子**。

零执行范围：影子代码没有CommandBus、loadfile、播放/暂停/切歌、历史/偏好写入或语音路由调用。MPV只读连接关闭不会退出播放器。数据库authorizer拒绝DELETE；缺失库不创建，损坏库不恢复，真实schema测试文件前后哈希及目录相同。
