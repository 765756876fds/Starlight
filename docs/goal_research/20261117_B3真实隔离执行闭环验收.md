日期：2026-11-17，Asia/Shanghai。基线 `1853316f7c13b9324d6d69d1653ce6c0bc5057c9`，分支 `a0-cleanup`。

## 结论

**同一个LISTEN_MUSIC已在隔离环境中，根据实际状态分别选择NO_OP、RESUME_MUSIC、TRY_COLLECTION、TRY_CHART；后三者通过现有音乐业务与真实MPV取得匹配路径、未暂停和进度推进证据。** 不是将合成STARTED作为真实结果。

TRY_CHART的资源全部由本地确定性替身提供，经过真实推荐、URL处理、loadfile和队列链路；它不证明真实在线平台可用。NO_OP只是已有目标继续成立，没有新起播、没有业务调用。

**暂不建议接入用户正式实例。唯一主要阻塞是缺少统一、权威的原子执行契约**：把播放器/成员/资源revision及请求代次校验，与业务受理及可归属的起播/失败回执连在一起。当前收藏入口的检查与调用不是生产范围内的原子操作，实验门闩不能代替正式入口契约。无需再研究GOAP或下载模型来解决这个问题。

## 1. 继承与隔离

- B1：复用Goal/GoalConstraints、稳定身份、独立只读MPV端口。B2：复用World、Capability、Plan、Decision、比较器、Action和Outcome，不改原契约或冻结数据。
- B3只新增Observation/Result封套，将真实读取映射成B2世界，ACCEPTED单独记录；不创建另一套规划、推荐或播放器算法。
- 干净HEAD归档副本 `D:/starlight-b3-5d2f4051/candidate`，只叠加本轮新增文件。原有未提交控制器、MPV和fixture修改没有混进实验基线。
- 每个Lab新建music.db/music_preferences.db、成员/歌单、配置/下载路径和媒体目录；MusicController、CommandBus、EventBus、StateStore、OnlineSourceManager均为独立实例。
- MPV唯一命名管道、--no-config、--load-scripts=no、--ao=null、--vo=null，不读取用户播放器配置。现有启动器的TLS参数由实验参数明确覆盖为verify=yes，没有网络请求或系统网络修改。
- 禁止探测生成目录外媒体；Lx连接探测在实验装配层禁用，扫描/高潮分析后台任务不启动。没有正式主窗口、ASR、TTS、交互学习或用户插件参与。
- 子进程上限20秒，正常close后有限join所有本实例新线程。异常恢复核对PID/创建时间/binary/唯一IPC后只回收自有进程。生成数据、原始日志不提交。

## 2. 选择、二次检查和业务路径

capture在工作线程读取真实MPV idle/path/pause/time-pos及后续进度、控制器请求/会话代次、队列快照、正常mode=ro WAL成员快照、精确音源注册版本及文件身份。读取前后控制器stamp不一致则世界过期。

execute再次capture，核对世界、候选、成员内容身份、文件状态、音源版本和实验manual_revision。活动/未知影视状态不给新播放授权。旧结果不允许覆盖后续手动选择。

| 计划 | 实际路径 | 确认证据 |
| --- | --- | --- |
| NO_OP | 二次只读采样，不进入业务handler | 目标已有进度，无新loadfile、无队列或DB变更 |
| RESUME_MUSIC | 自有CommandBus → MUSIC_RESUME → 既有resume(_voice_guard) → MPV | 独立记录pause=false IPC响应，再观察原路径实际推进 |
| TRY_COLLECTION | B2成员快照 → 稳定成员ref → 真实临时成员行 → play_playlist_item → play_song | 不采用旧bool作为起播证明；按预期本地路径观察推进 |
| TRY_CHART | 自有CommandBus → MUSIC_RECOMMEND → RecommendationService → 本地源目录/详情/解析 → play_online/loaded建队列 | 原推荐返回与独立MPV推进交叉验证 |

资源只可尝试时goal_satisfied=false。业务返回None/True、loadfile success均不是起播确认；暂停属性变更也需后续推进。NO_OP的Outcome.STARTED表示“已有目标被再次观察到”，accepted=false、attempts=0，不能统计为新播放。

明确业务接口差异：收藏play_playlist_item没有expected_request/guard参数，实验只能用自己的action_gate串行化自己模拟的手动操作；正式UI、自然接续等调用方并不共享此门闩。推荐已有expected_request、is_current及紧贴loadfile复核，可直接用于隔离试验。

## 4. 失败处理与仍缺的保证

实验外层最多2个计划，推荐宏最多调用一次；总预算最高5秒，经现有guard传给推荐。RecommendationService原有3榜单/4候选、20秒读取与45秒总守卫未改；外层没有创建3×45秒预算，也没有复制内部换源算法。源码仍可能有已运行future不能强制终止的边界，因此只使用最长2秒、可由Event释放的本地源。

H安全回退属于**受控业务前拒绝故障注入**，随后榜单确实通过真实业务播放；不是“真实解码失败后也能安全回退”的证明。真实损坏文件和发送前拒绝都暴露旧入口可能先改队列/记录尝试，原型保守停止，不擅自回滚用户记录或宣称副作用已撤销。

F的临时DB连接确有10次现有SQL变更（包括原业务计数/历史），不代表10次喜欢，也不代表播放成功。B3没有增加偏好判断或更改这些生产语义。确认失败时仍可能存在原控制器的自动跳过，测试结束立即正常停止隔离控制器并join；未证明正式长期运行已完全取消所有在途动作。

要获得生产级授权，需要一个最小的compare-and-apply接口：携带播放器/手动状态revision、请求代次、成员及音源revision，在真正副作用前统一复核，返回可关联的accepted/started/failed/stale及副作用状态。再由现有控制器处理播放，不新增播放器。只读API可后续稳定化，但本轮不修改正式源码。
