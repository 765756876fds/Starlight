# B2：活跃快照与可尝试能力验收

日期：2026-11-17；基线：`0a36a2a23a91ff10b069a266881d42cdd85266f0`，分支 `a0-cleanup`。

## 结论

方案 B 可以根据实际 MusicDatabase schema 的一致快照，以及有来源、时效和身份约束的可尝试证据，提出收藏或榜单方案；失败后能在合成执行器中有界收尾。**可尝试不等于已经起播，本轮没有真正执行任何新计划，也没有接管 LISTEN_MUSIC。**

活跃数据库优先继续研究 A：工作线程专用 `mode=ro` 连接、正常 WAL 可见性、短读事务、数量限制、busy/progress/cancel 与 finally 关闭。B 的所有者短锁更快，但必须由正式所有者提供接口，不能外部侵入其现有连接与回调。

B1 的 046/047 契约裁定、原始 61/63、冻结数据及外部测量未改动、未重跑。本轮没有 GOAP、模型、网络请求或生产钩子。

## 1. 活跃 SQLite 对照

| 项目 | A 独立只读事务 | B 所有者短锁聚合原型 |
| --- | --- | --- |
| 连接 | 新建专用 `mode=ro`，不加 immutable/shared cache | 仅接收实验 `LabOwner`，拒绝生产 MusicDatabase |
| 一致性 | BEGIN 后首个读固定快照，COUNT 与成员 SELECT 同事务 | 同样事务，并在所有者 RLock 内聚合 |
| WAL | 看见未 checkpoint 的已提交成员 | 同左 |
| 其他连接提交 | 本次仍看到旧一致版本，下次看到新版本 | 同左 |
| 失败 | total=None、unverified，不冒充空收藏 | 锁忙/关闭/事务忙同样待核验 |
| 生命周期 | 每次关闭专用连接，活动连接计数归零 | 保留所有者连接，实验结束显式关闭 |

真实临时库测试涵盖已提交 WAL、未提交写不可见、读期间写入、独占锁、取消、SQL progress 超时、恢复、路径替换、未知 schema、缺失、损坏、数量上限、原有写事务保护。读取限制默认64、上限256，LIMIT+1 检测部分结果；COUNT 仍有扫描成本，受 progress/预算约束。未知 schema 不能解释为空库。

SQLite 的 WAL 读事务维持固定 end mark，其他连接随后提交不改变本次快照。[SQLite isolation](https://www.sqlite.org/isolation.html)

`mode=ro` **不等于文件系统完全无变化**：正常 WAL 协调涉及 SHM，某些条件需要已有侧文件或目录可写，不能拿 SQL 只读声称所有侧文件不变。[SQLite WAL](https://www.sqlite.org/wal.html) 本轮未打开真实用户库，未对其 checkpoint、迁移、修复或重建；临时库的 schema 初始化和最后正常 close 属于实验写入者。

### 实际发现并修正的实验缺陷

B 初稿只设置 progress handler，未限制 SQLite 内部锁等待。外部连接持有 EXCLUSIVE 锁时，要求50ms，实际 **6344.0034ms**，证明进度回调不能覆盖 busy wait。

修正仅在实验 OwnerReadSnapshot：在短锁内保存 busy_timeout，临时设为剩余预算与20ms的较小值，finally 清回调并恢复原值5000。相同探针修后 **156.5452ms**，安全返回待核验，原 timeout 恢复。没有修改正式 MusicDatabase。

**仍不能承诺严格50ms墙钟截止**：SQLite busy handler 与系统调度可超出名义预算；本地断言为有界500ms，且在后台隔离。发生不可靠文件系统长阻塞时，进度回调也不构成强制中断任意 I/O 的保证。生产所有者锁必须进一步设计，不能把本实验包装为硬实时API。[busy timeout](https://www.sqlite.org/c3ref/busy_timeout.html)、[Python sqlite3 progress handler](https://docs.python.org/3.11/library/sqlite3.html)

## 2. 资源与结果契约

| 层次 | 本轮证据 | 不代表什么 |
| --- | --- | --- |
| RESOURCE_EXISTS | 成员记录或榜单目录存在 | 不代表归属、可解析或可播放 |
| OWNERSHIP_CONFIRMED | 可信个人库内歌单成员；固定喜欢歌单为明确保存信号 | 不从陌生库/歌名猜测归属 |
| ATTEMPTABLE | 有可靠身份、能力、时效，允许有界尝试 | 不代表 URL 已返回、MPV 已解码 |
| PLAYBACK_CONFIRMED | 必须由真实执行后起播证据提供 | 本轮合成 STARTED 不生成真实此证据 |
| UNVERIFIED | 读失败、身份/能力/时效不足 | 不是空库、也不是确定不可用 |
| UNAVAILABLE | 已确认缺失/不可读/关闭等 | 与缺少证明分开 |

四类结果独立：决策合法、业务接受、实际起播、用户满意。合成器分别记录 accepted 与 progressed，所有 user_satisfaction 均为 unobserved。没有进度的 STARTED 声称降为 UNKNOWN。

### 个人收藏

本地文件：显式允许根目录、普通文件、非空可读、已配置扩展名、检查前后身份/大小/mtime稳定，才可建议尝试。故意使用不能解码的 `.wav` 字节验证：上述条件仍不证明 MPV 解码成功，模拟失败正常收尾。

在线收藏：可信成员 + source_name/track_id + 精确已注册的 URL resolver + 新鲜代次，才可建议尝试。**不调用 resolver、不取得 URL、不测试付费或真实音源。** 当前只能安全读取精确音源注册表；需要调用 accepts() 的 JS 插件别名保持未知。关闭状态通过现有 executor 状态读取，未臆造 manager._closed。

明确喜欢权重优先于外部提供的历史证据；本轮没有自动读取真实偏好/历史库或新建学习系统。归属还依赖调用方确实验证“这是用户个人库”，不能仅凭路径名把任意库视为可信。

### 榜单

现有 RecommendationService 真实链路为目录 → 详情 → 候选 → URL解析 → play_online → loaded回调建队列 → 起播观察。已审查 MAX_CHARTS=3、MAX_TRIES=4、READ_TIMEOUT=20、MAX_PENDING_READS=2、play总体45秒 guard 和约2秒起播观察；正在运行的底层 future 不会仅因取消标记就被强行终止。

B2 只有在目录新鲜、精确音源具备详情和解析能力、现有服务未关闭/忙碌且契约匹配时，才提出“使用既有推荐业务准备并尝试”宏。目录不需要预先包含已验证的某首歌；这证明的是准备尝试能力，绝不证明其中歌曲必定可播。

**现有 play 不接收精确榜单ID**，因此只生成一个服务宏，不假装能够分别执行每个榜单，也不新增第二套选曲/换源回退。仅有榜名、ID、缓存而没有准备能力，仍是 NEEDS_VERIFICATION。

## 3. 决策与安全回退

优先顺序：硬约束和新鲜代次 → 已满足目标NO_OP → 可靠暂停会话RESUME → 明确偏好 → 历史证据 → 改变成本/稳定ID。正常同等证据下收藏先于榜单；明确不可尝试或待核验的收藏不阻止合法榜单方案。缺少所需标签则待核验，不伪造匹配。

明确保留内容时排除替换方案；要求新内容时不能用NO_OP或恢复原曲宣称完成。电影活跃或状态未知时，不能通过新计划擅自暂停电影；已经在播放音乐时NO_OP本身不改变电影。

NEEDS_VERIFICATION 表示缺技术证据，NEEDS_CLARIFICATION 表示目标/跨媒体策略歧义。前者仅提供向B1旧状态兼容映射，不接UI、不反复向用户追问技术细节。

合成执行器最多3次不同业务计划尝试、最多2次回退、默认总推导模拟预算200ms（上限1秒）。仅 FAILED/TIMEOUT 且确认没有播放副作用时回退。已经接受但完成不明、失败副作用不明、代次/资源过期都停止。不能因未收到确认就并发发出另一播放。

这些模拟毫秒预算不是推荐联网预算。未来接线必须共享既有总预算和取消guard，不能3次外层尝试各自给45秒，也不能重复执行推荐内部的3榜单/4歌曲回退。

## 6. 下一步最小接口和边界

可复用：MusicDatabase现有成员关系/schema、音乐控制器的当前请求代次、B1真实状态只读链、OnlineSourceManager注册/版本、RecommendationService现有准备/播放/队列/失败回退。B2没有调用这些生产写入或执行入口。

需要最小正式API，但**本轮只设计不实施**：

1. owner `read_collection_snapshot(limit, deadline, cancel)`：原生管理锁/回调，返回schema、完整性、成员revision、关闭/重建epoch；外部不能覆盖现有回调。当前文件inode与短TTL不足以替代成员变更revision。
2. `source_capabilities()`：明确稳定来源及JS别名映射、ready/closed/epoch，不主动联网。反射私有注册表只适用于当前研究，不是长期稳定接口。
3. 与请求代次、资源revision绑定的accepted/started/failed/stale及“确定无副作用”回执；重新核验后才允许尝试。当前资源刷新与generation检查只是纯契约，不构成生产取消机制。
4. 共享现有推荐总预算，定义候选宏参数与可取消边界；避免重复推荐算法和嵌套重试。

**具备继续隔离试验的条件，不具备直接上线自动播放的验收条件。** 活跃用户库权限、真实插件别名、在线可达性、MPV实际起播与取消效果、真实麦克风都未在本轮验收。无需用户为本次研究反复实测，也不要求先为每首歌取得起播证明；应在未来获准的执行试运行中验证结果。
